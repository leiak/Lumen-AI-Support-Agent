# Migrations (Alembic)

This directory contains the project's PostgreSQL schema migrations,
managed by [Alembic](https://alembic.sqlalchemy.org/).

## Quick reference

```bash
# Apply all pending migrations
cd apps/api
alembic upgrade head

# Roll back the last migration
alembic downgrade -1

# Generate a new migration after a model change
alembic revision --autogenerate -m "describe the change"

# Show current revision
alembic current

# Show migration history
alembic history --verbose
```

`alembic upgrade head` is also called by:

- `tests/e2e/global-setup.ts` (Playwright `globalSetup`) — runs once
  before the e2e suite starts
- `deploy/docker-compose.yml` — `migrate` one-shot service that runs
  before the api / web services come up (Pack C)
- `scripts/bring-up.sh` indirectly — same `migrate` one-shot

## File naming convention

Two naming styles coexist on purpose:

| Style | When | Example |
|-------|------|---------|
| `<ULID>_<slug>.py` | Auto-generated by `alembic revision --autogenerate` | `16008dafeff0_add_knowledge_base_tables.py` |
| `<NN>_<slug>.py`     | Hand-authored for fast-iteration milestones (M2.A / M2.B / M4.*) | `12_ticket_tables.py` |

The `<NN>_` numeric prefix is reserved for **manually authored** files
(used when we needed a clean migration ahead of autogenerate's
heuristics, e.g. M2.A's ticket ENUM switch from `cream-req` →
`ticketed`). Anything autogenerated uses the standard Alembic ULID
prefix.

When you create a new migration:

1. **If it's a quick schema fix**: use `alembic revision -m "..."` (no
   `--autogenerate`) and hand-write the upgrade/downgrade. File name:
   `<NN>_<slug>.py` where `<NN>` is one higher than the latest
   numeric-prefixed migration in this directory.
2. **If it's a model-driven change**: use `alembic revision
   --autogenerate -m "..."` and review the diff carefully — Alembic
   autogenerate misses column renames, ENUM value changes, and
   server-default expressions. Always run `alembic upgrade head`
   against a fresh DB and a DB that's one revision behind, to catch
   drift both directions.

## Operational notes

- **ENUM values**: lower-case only. The PG ENUM types `ticket_priority`
  and `ticket_status` use `'p0' / 'p1' / ...` and `'new' /
  'in_progress' / ...` (not the uppercase `Enum.name`). Models bind
  via SAEnum — when you add a new ENUM value, update both
  `apps/api/src/<domain>/enums.py` and the migration's
  `op.execute("ALTER TYPE ...")` block.
- **Timezone discipline**: every TIMESTAMP column is `TIMESTAMP WITHOUT
  TIME ZONE` (PG convention); the application always passes UTC
  `datetime` (tz-aware, then `.replace(tzinfo=None)` before INSERT).
  Don't introduce `TIMESTAMP WITH TIME ZONE` columns without a
  design review — the `LLMUsage.created_at` filter logic in
  `budget.resolver` assumes naive-UTC storage.
- **Idempotent seeds**: `tests/e2e/scripts/seed*.py` write
  deterministic primary keys (e.g. `01HZDEMO00000000000000000`) so
  re-running them hits unique-constraint no-op paths. Adding new
  rows? Pick a fresh fixed ULID prefix (`01HZDEMO…`) so existing
  databases aren't disturbed.

## CI

The `backend-integration` GitHub Actions job:

1. Spins up a fresh Postgres service container
2. Runs `alembic upgrade head` against it
3. Runs the integration tests (any migration that breaks the schema
   fails the build)

If your migration breaks step 2, you have a non-deterministic upgrade
path — usually a missing `op.execute("CREATE INDEX CONCURRENTLY ...")`
or an out-of-order column add. Fix forward with a follow-up migration
rather than editing the broken one.
